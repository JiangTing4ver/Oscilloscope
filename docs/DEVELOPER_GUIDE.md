### 为什么用 ARMCC 而非 GCC

底层驱动（`delay.c` / `lcd.c`）使用 ARMCC 方言的内联汇编与位带操作。改用 GCC 需要重写分散加载与 CMSIS 适配，成本远大于收益。

## 3. 构建系统

### 使用方式

```bat
build.bat              :: 增量编译，产物 build\Oscilloscope.hex / .axf
build.bat clean        :: 清理 build\
build.bat DEBUG=1      :: 带调试信息编译
```

### 三条硬性规则

| 规则 | 原因 |
|---|---|
| **必须通过 `build.bat` 调用** | 它把 `TMP`/`TEMP` 指向工程内 `.tmp\`。否则 ARMCC 编译含内联汇编的源码时会随机报 `#564: cannot open embedded assembler output file` |
| **不要给 make 添加 `-j`** | ARMCC 的内联汇编使用固定临时文件名，并行编译会互相覆盖 |
| **必须使用 `OBJ/Oscilloscope.sct`** | 其中三行规则缺一不可，见下 |

### 分散加载文件

```
*.o (RESET, +First)        ; 中断向量表必须位于镜像最开头
*(InRoot$$Sections)        ; C 库启动代码与数据段初始化
.ANY (+RW +ZI)             ; 读写数据与零初始化数据放入 RAM
```

**缺少任一行**时，链接仍会"成功"，但镜像无法启动，且链接器不会报错。

### 头文件依赖问题

**本 Makefile 只有 `%.o: %.c` 规则，没有头文件依赖规则。**

修改任何 `.h` 后执行 `build.bat`，make 会认为"无事可做"，**改动不会生效**。这是极易被误判为"代码没起作用"的陷阱。

**正确流程**：

```bat
build.bat clean
build.bat
```

### 镜像有效性校验

```powershell
$l = [IO.File]::ReadAllLines("build\Oscilloscope.hex")
$l | Where-Object { $_ -match '^:..000000' } | Select-Object -First 1
```

实测输出：

```
:1000000028270020E9010008...
```

解析结果 `SP = 0x20002728`（RAM 区间）、`PC = 0x080001E9`（Flash 区间），判定有效。

## 4. 软件架构

### 模块划分

```
main.c
  │
  ├─ 每 5ms：KEY_Scan()         按键状态机（消抖、长按、连发、双击）
  │           osc_ui_handle_key() 解释事件，更新仪器参数
  │
  └─ 每 5ms：osc_ui_update()
               ├─ osc_trigger_capture()   从环形缓冲截取一屏
               ├─ osc_measure_run()       或 osc_fft_run()
               └─ 绘制（状态栏 / 波形区 / 测量栏）

后台（硬件自主运行，不占 CPU）：
  TIM2 ──TRGO──> ADC1 ──DMA请求──> DMA1_CH1 ──> s_ring[]
```

### 数据流

```
s_ring[2048]  ──(触发搜索 + 拷贝)──>  g_wave[320]  ──> 测量/FFT  ──> 屏幕
 （DMA 持续写入）                      （一屏快照）
```

`g_wave` 是逻辑与显示之间唯一的数据交换点，由 `osc_trigger.c` 定义并维护。

### 模块职责

| 模块 | 文件 | 职责 |
|---|---|---|
| 采样链路 | `osc_adc.c` | ADC、DMA、TIM2 配置；时基与通道管理；环形缓冲访问 |
| 触发捕获 | `osc_trigger.c` | 边沿搜索、模式管理、一屏数据拷贝 |
| 自动测量 | `osc_measure.c` | Vpp / Vrms / 频率计算 |
| 频谱分析 | `osc_fft.c` | 定点 FFT、加窗、幅度归一化 |
| 界面交互 | `osc_ui.c` | 绘制与按键语义解释 |
| 按键驱动 | `osc_key.c` | 四类按键事件的生成与分发 |

## 5. 采样链路设计

### 5.1 硬件触发链

```
TIM2 计数器 ──到达 CCR2──> 比较事件 ──映射到 TRGO──> ADC1 外部触发
                                                        │
                                                  启动一次转换
                                                        │
                                             转换完成 ──> DMA 请求
                                                        │
                                          DMA1_CH1 搬一个半字到 s_ring
```

**为什么用"定时器比较事件"而不是"更新事件"作为触发源**

`ADC_ExternalTrigConv_T2_CC2` 是标准外设库中与 TIM2 关联的触发源之一。使用比较事件的好处是触发时刻由 CCR2 决定，在每个计数周期内的位置固定，抖动更小。代码中把 CCR2 设为固定小值（`TIM_Pulse = 1`），使触发点紧邻计数周期起点。

**为什么 DMA 用循环模式**

示波器需要"永远有新数据"。循环模式下 DMA 填满缓冲后自动从头覆盖，无需软件介入，也就避免了"停止 DMA → 处理 → 重启 DMA"过程中丢失的数据。

### 5.2 时基换算

```
计数频率 = 72MHz / (PSC + 1)
采样率   = 计数频率 / (ARR + 1)
```

时基表统一取 `PSC = 8`（计数频率 9MHz），因此 `采样率 = 9MHz / (ARR+1)`：

| PSC | ARR | 采样率 | 每格时间（32 点/格） |
|---|---|---|---|
| 0 | 7199 | 10 kHz | 3.2 ms |
| 0 | 14399 | 5 kHz | 6.4 ms |
| 0 | 35999 | 2 kHz | 16 ms |
| 1 | 35999 | 1 kHz | 32 ms |
| 11 | 59999 | 100 Hz | 320 ms |
| 119 | 59999 | 10 Hz | 3.2 s |

最后一档单独使用 `PSC = 89`，因为若沿用 9MHz 计数频率，ARR 需要 8999，虽然仍在 16 位范围内，但为保持表格规律性，改用更大的预分频。

### 5.3 采样率上限的推导

```
ADC 时钟     = PCLK2 / 6 = 12 MHz
转换时间     = (采样时间 + 12.5 个 ADC 周期) / ADC 时钟
             = (1.5 + 12.5) / 12MHz
             ≈ 1.17 µs
```

因此 ADC 单次转换理论上只需约 1.2 µs，理论采样率可达 800 ksps 以上。

**但实际可用采样率远低于理论值 ——— 这是本项目最重要的实测结论**

屏幕刷新时 CPU 全速写 GPIO 数据总线（每像素一次写操作），
DMA 控制器与 CPU 竞争 AHB 总线，取走 ADC 结果的时机被推迟。
当 ADC 转换完成而 DMA 尚未取走数据时，新结果会覆盖旧结果并置位 OVR，
造成采样点丢失。

逐档实测数据：

| 标称采样率 | 实测采样率 | 达成率 | 结论 |
|---|---|---|---|
| 20 kHz | 0.8 kHz | 4% | ❌ 严重丢点 |
| **10 kHz** | **9.7 kHz** | **97%** | ✅ 最高可用档 |
| 5 kHz | 4.8 kHz | 96% | ✅ |
| 2 kHz | 1.9 kHz | 96% | ✅ |
| 1 kHz | 0.96 kHz | 96% | ✅ |
| 100 Hz | 96 Hz | 96% | ✅ |
| 10 Hz | 9.7 Hz | 97% | ✅ |

因此时基表最高档位限定为 **10 kHz**。

> **若要突破此限制**，可从两方面入手：
> 1. 降低屏幕刷新率（牺牲界面流畅度换取采样带宽）
> 2. 改用带 DMA 的并口/SPI 屏方案，让屏幕刷新不占用 CPU 总线周期

**测量方法说明**：本次结论通过统计 DMA 传输计数器的位移速率得到。
必须让 CPU 自由运行（不能处于调试暂停状态）时测量，
因为调试暂停会同时冻结外设时钟，测得的速率为 0。

### 5.4 环形缓冲的尺寸选择

`OSC_RING_SIZE = 2048`（4 KB）的考虑：

| 因素 | 说明 |
|---|---|
| 必须是 2 的幂 | 取模运算可退化为按位与 `& (SIZE-1)`，拷贝时无需分支处理回绕 |
| 容量应远大于一屏 | 一屏 320 点，2048 点可容纳 6 屏，使触发搜索有足够回溯空间 |
| 触发搜索上限 | 代码限制回溯半个缓冲（1024 点），避免搜索耗时过长 |
| RAM 预算 | 4 KB 只占 48 KB 的 8% |

## 6. 触发与捕获

### 6.1 为什么"向后搜索"而不是"等待触发"

传统思路是：等待触发条件成立 → 开始采样 → 填充一屏。本工程采用相反的做法：

```
DMA 持续采样（永不停）  →  在已有数据中向后找边沿  →  以边沿为基准截取一屏
```

| 优势 | 说明 |
|---|---|
| 不会漏触发 | 数据一直在缓冲里，不存在"触发时采样还没启动"的窗口 |
| 无需重启 DMA | 切换时基、通道、触发电平时波形不中断 |
| 天然支持预触发 | 可以从边沿点**往前**多取若干点，显示触发之前发生的波形 |
| 实现简单 | 只是一个数组遍历，不涉及状态机与中断协作 |

**代价**：需要遍历缓冲，复杂度 O(n)。代码限制回溯 1024 点，最坏情况遍历约 1024 次比较，在 72MHz 下耗时不足 50 µs，可忽略。

### 6.2 预触发实现

```c
#define OSC_PRETRIG_POINTS  32

base = (start + OSC_RING_SIZE - OSC_PRETRIG_POINTS) & (OSC_RING_SIZE - 1);
```

起点向前偏移 32 点，使触发点落在屏幕约 1/10 处，从而能观察到触发**之前**的波形。这正是示波器"预触发"功能的原理。

### 6.3 三种模式的行为差异

| 模式 | 找到边沿 | 未找到边沿 |
|---|---|---|
| AUTO | 以边沿为基准对齐显示，`g_wave_valid = 1` | 从写指针直接取一屏（自由滚动），`g_wave_valid = 0` |
| NORMAL | 同 AUTO | **不做任何更新**，保持上一屏 |
| SINGLE | 同 AUTO，但捕获后清除武装标志 | 不更新（且不会自动重新武装） |

`g_wave_valid` 同时用于状态栏的颜色提示（青色 = 已同步，灰色 = 自由滚动）。

## 7. 自动测量算法

### 7.1 Vpp / Vavg

一次遍历同时求出极值与累加和：

```
Vpp  = (Vmax - Vmin) × VREF / 4095
Vavg = (Σv / n) × VREF / 4095
```

### 7.2 Vrms

```
Vrms = sqrt( Σ(v²) / n ) × VREF / 4095
```

**实现细节**：先对 ADC 原始值求均方根，最后统一换算为电压，可减少一次除法带来的精度损失。

**整数平方根**：为避免链接数学库，代码中实现了逐位逼近的开方算法（不使用 `sqrt()`）：

```c
u32 bit = 1UL << 30;
u32 res = 0, num = mean_sq;

while (bit > num) bit >>= 2;
while (bit != 0)
{
    if (num >= res + bit) { num -= res + bit; res = (res >> 1) + bit; }
    else                    res >>= 1;
    bit >>= 2;
}
```

这是经典的"逐位开方"（digit-by-digit square root）算法，只用加减与移位，全程整数运算。

### 7.3 频率测量

**算法**：

```
1. 求出 Vmax 与 Vmin，取中点 mid = (Vmax + Vmin) / 2 作为判决电平
2. 扫描波形，记录所有"从 mid 以下跨越到 mid 以上"的位置
3. 周期点数 = (最后一次跨越位置 - 第一次跨越位置) / (跨越次数 - 1)
4. 频率 = 采样率 / 周期点数
```

**为什么用中点而不是固定电平**

信号可能带直流偏置，固定电平可能落在波形范围之外。用 `(Vmax+Vmin)/2` 能自适应任何幅度的信号。

**为什么至少需要两次跨越**

一次跨越无法确定周期。屏上不足两个周期时，函数返回 0，界面显示 `----`。

**局限性**：对谐波丰富的信号（如方波、三角波），中点上可能出现多次抖动跨越，导致周期点数偏小、频率读数偏大。此时应改用 FFT 主频。

## 8. 频谱分析

### 8.1 算法流程

```
1. 减去直流分量（用一屏数据的平均值作为参考）
2. 加汉宁窗：x[i] = (s[i] - mid) × w[i]
3. 位反转重排
4. log2(N) 级蝶形运算
5. 计算各频点幅度，求最大值后归一化并作对数压缩
```

### 8.2 定点化设计

**汉宁窗（Q15）**

```
w[i] = 0.5 - 0.5·cos(2πi / (N-1))      取值范围 0 ~ 1
w_q15[i] = round(w[i] × 32767)         存储为 s16
应用：x = (v × w_q15[i]) >> 15
```

**旋转因子（Q15）**

```
sin_tab[k] = round(sin(2πk/N) × 32767)   k = 0 ~ N/4，共 65 项
```

只需保存 0 ~ 90 度的正弦值，其余象限通过对实部虚部加符号与角度平移得到：

| 象限 | cos | sin |
|---|---|---|
| 0 | `c` | `s` |
| 1 | `-s` | `c` |
| 2 | `-c` | `-s` |
| 3 | `s` | `-c` |

其中 `s = sin_tab[q]`，`c = sin_tab[SIN_LEN - q]`（利用 `cos(t) = sin(90°-t)`）。

**蝶形运算中的定点还原**

```
tr = (re_b × wc - im_b × ws) >> 15
ti = (re_b × ws + im_b × wc) >> 15
```

Q15 系数相乘会放大 2^15 倍，右移 15 位还原。

### 8.3 为什么把表做成编译期常量

初版在初始化时用 `sin()` / `cos()` 生成表，导致：

- 需要链接数学库（浮点三角函数），Flash 增加约 3 KB
- 首次调用时有数百次浮点运算开销

改为**编译期预计算的常量数组**后：

| 项目 | 改进 |
|---|---|
| 数学库依赖 | 完全消除 |
| Flash 占用 | 29.30 KB（减少约 3 KB） |
| 首次调用开销 | 无（表已在 Flash 中） |
| RAM 占用 | 减少 512 字节（汉宁窗表移出 RAM） |

常量表由 `osc_fft.c` 中的数组字面量提供，生成方式见第 11.3 节。

### 8.4 幅度归一化与对数压缩

**为什么用对数刻度**

线性刻度下，弱谐波会被基频完全淹没。对数刻度（30 dB 动态范围）能让强弱谱线同时可见。

**整数对数近似**

用最高有效位之差近似 `log2` 比值：

```
bit_max = max_mag 的最高有效位序号
bit_cur = mag_sq 的最高有效位序号
差值 1 位 ≈ 6 dB
30 dB 动态范围 = 5 位
level = 100 - 差值 × 20      （差值 ≥ 5 时取 0）
```

**为什么用幅度平方比较**

开方是单调运算，不影响"谁最大"的判断，因此直接比较 `re² + im²` 可省去 128 次开方。

### 8.5 频率轴映射

```
bin 对应频率 = bin × 采样率 / FFT_N
最高显示频率 = 采样率 / 2（奈奎斯特频率，对应 bin = 128）
```

显示时把 128 个 bin 归并为 64 列，每列取该区间内的**最大值**（而非平均值），避免窄带峰值被稀释。

## 9. 界面与渲染

### 9.1 刷新策略

| 区域 | 刷新时机 | 原因 |
|---|---|---|
| 状态栏 | 仅参数或运行状态变化时 | 内容变化少，全屏重绘浪费 |
| 波形区 | 每帧 | 波形每帧都变 |
| 测量栏 | 每帧 | 数值每帧都变 |

波形区**不做**增量更新（不追踪新旧波形差异），而是整体重绘：清背景 → 画网格 → 画触发线 → 画波形。

**理由**：网格重绘只有约 1400 个像素（18 条直线），而逐像素比对波形差异需要遍历 320 点并记录旧路径，代码复杂度与实际耗时都更高。

### 9.2 波形映射

```c
y = WAVE_Y0 + (WAVE_H - 1) - (adc × (WAVE_H - 1)) / 4095
```

- `WAVE_Y0` 为波形区上边界，`WAVE_H` 为高度
- 用 `(WAVE_H - 1)` 而非 `WAVE_H` 是为了让 `adc = 0` 时落在最后一行的有效像素上
- 电压升高对应 `y` 减小（屏幕上移），因此用减法

横坐标：

```c
x = (i - 1) × SCR_W / OSC_VIEW_POINTS     /* 320 个点铺满 320 像素 */
```

由于 `OSC_VIEW_POINTS == SCR_W == 320`，该映射实际为恒等，但保留计算式以便将来支持"一屏点数多于像素数"时的抽点显示。

### 9.3 绘制基元选择

| 用途 | 使用函数 | 原因 |
|---|---|---|
| 清背景、填充柱状条 | `LCD_Fill` | 块填充，走硬件连续写，最快 |
| 网格、波形、触发虚线 | `LCD_DrawLine` | 已实现的 Bresenham 直线 |
| 文字 | `LCD_ShowString` | 内置 12 号 ASCII 点阵字库，无需额外字库 |

**未使用 `LCD_DrawPoint` 逐点绘制波形**，因为逐点调用会有函数调用开销，而 `LCD_DrawLine` 内部会优化连续像素的写入。

## 11. 开发过程中的问题记录

以下问题在开发中实际遇到并已修正，修改代码时请勿回退这些处理。

### 11.1 汉宁窗定点格式不匹配（严重）

**现象**：频谱柱状图全为 0 或完全错乱。

**原因**：汉宁窗系数按 Q16 精度生成（最大值 65535），但存储类型为 `s16`（最大 32767）。

```c
static const s16 s_hann[FFT_N] = { ..., 65533, ... };   /* 65533 超出 s16 范围 */
```

65533 被截断为 `65533 - 65536 = -3`，窗系数在峰值区变成负数，加窗后波形被反相破坏。

**修正**：改用 Q15 精度（最大值 32767），与 `s16` 匹配：

```c
hann[i] = round((0.5 - 0.5·cos(2πi/(N-1))) × 32767)
#define HANN_Q  15
```

**教训**：定点数的 Q 格式必须与存储类型匹配。Q16 需要 `u16` 或无符号处理，用有符号 16 位时上限是 Q15。

### 11.2 按键事件被重复消费导致死代码

**现象**：编译通过但某些按键功能永不生效。

**原因**：初版在两个地方分别调用 `KEY_GetEvent()`。由于该函数**读取后即清零**，第二次调用永远返回 `NONE`：

```c
if (KEY_GetEvent(KEY_ID_1) & KEY_EV_DOUBLE) { /* 永远不执行 */ }
```

**修正**：函数开头一次性取出全部事件并保存到局部变量，后续只使用局部变量。

**教训**：消费型接口（read-and-clear）只能调用一次。

### 11.3 函数定义顺序导致的隐式声明

**现象**：编译告警 `function declared implicitly`，参数类型不匹配时可能引入难以排查的运行时错误。

**原因**：`KEY_Init()` 中调用了定义在其后的 `key_read_raw()`。

**修正**：在文件开头添加前置声明：

```c
static u8 key_read_raw(u8 id);
```

### 11.4 定时器触发相关的宏名错误

**现象**：编译报 `TIM_OCMode_PulseWidthModulation` 与 `TIM_TRGO_OC2REF` 未定义。

**原因**：凭记忆写了 STM32 HAL 库风格的宏名，而标准外设库（SPL）的命名不同。

**修正**：

| 错误写法 | 正确写法（SPL） |
|---|---|
| `TIM_OCMode_PulseWidthModulation` | `TIM_OCMode_PWM1` |
| `TIM_TRGO_OC2REF` | `TIM_TRGOSource_OC2Ref` |

**教训**：写外设库调用前，先在 `STM32F10x_FWLib/inc/` 中确认宏名，不要凭记忆下笔。

### 11.5 `u64` 类型不存在

**现象**：编译报 `identifier "u64" is undefined`。

**原因**：STM32 标准外设库只定义了 `u8` / `u16` / `u32`，没有 `u64`。

**修正**：使用标准 C 类型 `unsigned long long`。

### 11.6 按键驱动与旧驱动符号冲突

**现象**：链接报 `Symbol KEY_Init multiply defined (by osc_key.o and key.o)`。

**原因**：新写的 `osc_key.c` 与从旧工程带过来的正点原子 `key.c` 都定义了 `KEY_Init` / `KEY_Scan`。

**修正**：删除旧的 `key.c` / `key.h`，并从 Makefile 移除。

**注意**：`osc_key.c` 的 `KEY_Init()` **保留**了旧驱动中 `GPIO_Remap_SWJ_JTAGDisable` 的调用，这一句必须保留，原因见第 13.4 节。

### 11.7 常量表初始化与 `const` 冲突

**现象**：把汉宁窗表声明为 `const` 后，初始化代码无法对其赋值。

**修正**：改为编译期预计算常量数组（表值由脚本生成并写入源码）。

**生成方式**：使用 Python 脚本计算并格式化输出 C 数组字面量，避免手工誊写 256 个常量出错。

### 11.8 ADC1 不支持 TIM2_TRGO 作为触发源

**现象**：按"TIM2 更新事件 → TRGO → 触发 ADC"的思路配置后，ADC 完全不转换，
`DMA1_CNDTR1` 恒为初始值 2048。

**原因**：STM32F103 的 ADC1 可选外部触发源是**固定枚举**，共 7 项：

```
T1_CC1 / T1_CC2 / T1_CC3 / T2_CC2 / T3_TRGO / T4_CC4 / EXT_IT11
```

其中**没有 TIM2_TRGO**。虽然 TIM2 能把更新事件输出到 TRGO，
但 ADC1 的触发选择器里没有对应选项，该方案在硬件上不可行。

**修正**：改用 **TIM4_CC4**（`ADC_ExternalTrigConv_T4_CC4`）。
TIM3 已被 1ms 系统时基占用，故选用 TIM4。

**附带问题**：初版用 `TIM_OC2Init` 配置比较通道时传入了
`TIM_OutputState_Disable`，本意是"不输出到引脚"。但标准外设库中该参数
同时控制通道使能位 `CCER.CCxE`，置 Disable 等于关闭整个比较通道，
`OC2REF` 永远为低电平，TRGO 也就不产生事件（实测 `CCER = 0x00000000`）。

**教训**：写外设库调用前先在 `STM32F10x_FWLib/inc/` 中确认触发源枚举与参数语义，
不要凭其他库（如 HAL）的印象下笔。

### 11.9 时基表参数与标称频率不一致

**现象**：时基档位标注"20 kHz"，但实际采样率只有标称值的 4%。

**原因**：编写时基表时**把想要的频率直接当成了 ARR 值**，没有按公式反算：

```c
/* 错误：psc=8、arr=44 代入公式得到 177777Hz，却标注为 20000Hz */
{ 8, 44, 20000 },
```

`72MHz / ((8+1) x (44+1)) = 177777 Hz`，与标注的 20000 Hz 相差 8.9 倍。

**修正**：建立"目标频率 → PSC/ARR"的反算流程，保证 `fs` 字段与
`72MHz / ((PSC+1) x (ARR+1))` 严格一致：

| 目标 | PSC | ARR | 实际 |
|---|---|---|---|
| 10 kHz | 0 | 7199 | 10000.0 Hz |
| 5 kHz | 0 | 14399 | 5000.0 Hz |
| 1 kHz | 1 | 35999 | 1000.0 Hz |

**验证方法**：从 elf 中 dump 表内容并逐项核算，而不是只读源码。

**教训**：配置类常量表需要自动化校验，不能靠肉眼。

### 11.10 DMA 吞吐能力决定采样率上限

**现象**：修正上述两项后，标称 10 kHz 可达 97%，
但标称 20 kHz 时实际只有 824 Hz（4%）。

**原因**：屏幕刷新时 CPU 全速写 GPIO 数据总线（每像素一次写操作），
与 DMA 控制器竞争 AHB 总线。DMA 取走 ADC 结果的时机被推迟，
转换结果被新结果覆盖而丢失。

这不是配置错误，而是该硬件架构下的**吞吐量上限**。

**修正**：时基表最高档位限定为 **10 kHz**（实测达成率 97%）。

**若要突破此限制**，有两个方向：

1. 降低屏幕刷新率（牺牲界面流畅度换取采样带宽）
2. 改用带 DMA 的并口/SPI 屏方案，让屏幕刷新不占用 CPU 总线周期

**测量注意事项**：统计 `DMA1_CNDTR1` 位移速率时必须让 CPU 自由运行。
目标若处于调试暂停状态，外设时钟同时被冻结，测得的速率恒为 0。

## 12. 调试与验证方法

### 12.1 串口输出

| 参数 | 值 |
|---|---|
| 波特率 | 9600 |
| 数据位 / 停止位 / 校验 | 8 / 1 / None |

正常启动输出：

```
===== Mini Oscilloscope boot =====
LCD ID=0x9341  320x240
Sample rate = 100000 Hz, channel = PA1
```

`LCD ID=0x9341` 表示屏幕识别成功；`0x0000` 表示屏幕通信失败。

### 12.2 分级验证方法

示波器是"自己测自己"的设备，验证必须分层次，否则一旦没波形无法判断是哪一环出错：

| 层次 | 验证方法 | 通过判据 |
|---|---|---|
| 1. 屏幕 | 上电看界面 | 出现网格与状态栏 |
| 2. ADC | PA1 接 GND | 波形为贴近底部的直线 |
| 3. ADC 满量程 | PA1 接 3.3V | 波形为贴近顶部的直线 |
| 4. 采样率 | 接入已知频率信号（如 TIM 输出 1kHz PWM） | 测量栏频率读数接近 1kHz |
| 5. 触发 | 观察波形是否静止 | 波形稳定不横向滚动 |
| 6. 测量 | 对比万用表读数 | Vpp 与万用表测量值接近 |

**第 2、3 层是最关键的**：这两步通过，说明 ADC、DMA、环形缓冲、屏幕绘制整条链路正常，问题只可能在信号接入侧。

### 12.3 无串口时的寄存器检查法

通过 ST-Link 读取芯片内部状态诊断。

**判断程序是否运行**：

```python
from pyocd.core.helpers import ConnectHelper
s = ConnectHelper.session_with_chosen_probe(options={"target_override": "stm32f103rc"})
s.open(); t = s.target
for _ in range(10):
    t.halt(); print(hex(t.read_core_register("pc"))); t.resume()
```

PC 持续变化表示程序在运行；若始终停在同一地址，对照符号表定位卡死位置：

```powershell
arm-none-eabi-nm -n -S --defined-only build\Oscilloscope.axf > build\symbols.txt
```

**检查采样链路是否工作**：

| 寄存器 | 地址 | 含义 |
|---|---|---|
| `RCC_APB2ENR` | `0x40021018` | bit2 (GPIOA)、bit9 (ADC1) 应为 1 |
| `RCC_APB1ENR` | `0x4002101C` | bit0 (TIM2)、bit1 (TIM3) 应为 1 |
| `RCC_AHBENR` | `0x40021014` | bit0 (DMA1) 应为 1 |
| `ADC1_CR2` | `0x40012408` | bit0 (ADON) 应为 1，表示 ADC 已使能 |
| `DMA1_CCR1` | `0x40020008` | bit0 (EN) 应为 1，表示 DMA 通道已使能 |
| `DMA1_CNDTR1` | `0x4002000C` | **持续变化**表示 DMA 正在搬运数据 |

**`DMA1_CNDTR1` 是最直接的判据**：连续读取两次，若数值在变化，说明"TIM2 触发 → ADC 转换 → DMA 搬运"整条链路都在正常工作。

### 12.4 使用调试器

VS Code 中按 `F5`（配置见 `.vscode/launch.json`）：

| 配置 | 用途 |
|---|---|
| Debug (pyOCD autostart) | 编译 + 烧录 + 停在 `main` |
| Attach to external server | 附着到手动启动的 GDB 服务 |
| Attach (pyOCD autostart, no build) | 附着到运行中的芯片，不重新编译 |

**注意**：中断 DMA 与定时器后，采样会暂停，观察 `s_ring` 内容时需留意这一点。

### 12.5 常见问题的定位路径

| 现象 | 优先检查 |
|---|---|
| 屏幕花屏 | `KEY_Init()` 是否在 `osc_ui_init()` 之前调用 |
| 屏幕全白 | TFT 排线；串口的 `LCD ID` |
| 程序卡住（界面无响应） | pyOCD 读 PC，对照符号表 |
| 波形为直线不动 | PA1 是否接到固定电平；时基是否太慢 |
| 波形乱跳 | 触发电平是否在波形范围内 |
| 频率显示 `----` | 屏上是否不足两个周期 |
| 频谱全为 0 | 汉宁窗精度格式（见 11.1）；输入是否加偏置 |

## 13. 移植与扩展指南

### 13.1 更换显示屏

| 步骤 | 说明 |
|---|---|
| 1 | 确认新屏控制器在 `lcd.c` 支持列表中，否则需补充初始化序列 |
| 2 | 修改 `osc_ui.c` 中的 `SCR_W` / `SCR_H` 与版面参数（`BAR_H` / `WAVE_Y1` / `INFO_Y`） |
| 3 | 若分辨率变化较大，需调整网格格数（`draw_grid()` 中的循环次数） |

**注意**：`OSC_VIEW_POINTS` 与屏幕宽度相关。当前两者都是 320，横向映射为恒等；若屏幕宽度改为 240，应同步调整 `OSC_VIEW_POINTS` 或在 `draw_waveform()` 中做抽点。

### 13.2 增加垂直档位（增益切换）

当前波形固定按 0 ~ 3.3V 满量程显示。加入增益只需修改映射公式：

```c
/* 在 osc_ui.c 中增加增益状态 */
static u8 s_gain = 0;       /* 0=1x, 1=2x, 2=4x */
static const u8 s_gain_tab[3] = { 1, 2, 4 };

/* 映射时先乘增益再限幅 */
u32 v = (u32)g_wave[i] * s_gain_tab[s_gain];
if (v > 4095) v = 4095;
y = WAVE_Y0 + (WAVE_H - 1) - (v * (WAVE_H - 1)) / 4095;
```

同时需在测量模块中对 Vpp / Vrms 做相应的除法还原。

### 13.3 增加串口波形导出

`g_wave` 中已有一屏完整数据，导出只需逐个格式化输出：

```c
void osc_export_csv(void)
{
    u16 i;
    printf("index,adc,mv\r\n");
    for (i = 0; i < OSC_VIEW_POINTS; i++)
    {
        printf("%u,%u,%u\r\n", i, g_wave[i], osc_adc_to_mv(g_wave[i]));
    }
}
```

**注意**：串口 9600 波特率下输出 320 行约需 8 秒，界面会明显卡顿。建议在导出前停止刷新，或提高波特率。

### 13.4 移植到其他芯片时必须保留的处理

**`KEY_Init()` 中的 JTAG 释放**

```c
GPIO_PinRemapConfig(GPIO_Remap_SWJ_JTAGDisable, ENABLE);
```

2.8 寸 TFT 使用 PB0~PB15 作为 16 位数据总线，其中 **PB3 与 PB4 默认功能为 JTAG 的 JTDO / NJTRST**。不释放这两个引脚，数据线会缺失两位，屏幕显示花絮。

因此该语句必须在 `LCD_Init()` 之前执行。这是移植到任何使用 PB3/PB4 的板子时都必须注意的点。

### 13.5 FFT 表重新生成

若修改 `FFT_N`（当前 256），需要重新生成汉宁窗与正弦表。生成脚本思路：

```python
import math
FFT_N = 256
SIN_LEN = FFT_N // 4

hann = [round((0.5 - 0.5*math.cos(2*math.pi*i/(FFT_N-1))) * 32767) for i in range(FFT_N)]
sin_tab = [round(math.sin(2*math.pi*k/FFT_N) * 32767) for k in range(SIN_LEN + 1)]
```

**注意**：`FFT_N` 必须是 2 的整数次幂，且 `SIN_LEN = FFT_N/4` 也必须是 2 的幂（`twiddle_get` 中的取模运算依赖这一点）。

### 13.6 增加逻辑分析仪模式

STM32F103 的 DMA 只能由 ADC、SPI、USART 等外设触发，不能直接搬运 GPIO 状态。实现数字通道采集的思路：

| 方案 | 说明 |
|---|---|
| 定时器中断读取 | 在 TIM 中断中读 `GPIOx->IDR`，但采样率受中断开销限制（约 100 ksps） |
| 用 SPI 模拟 | 把 8 路数字信号接到 SPI 的 MISO 等引脚，用 SPI 时钟采样（复杂） |
| 降低目标采样率 | 接受 50 ~ 100 ksps，用定时器中断直接读取，实现简单 |

## 14. 编码规范

### 文件头注释

每个 `.c` / `.h` 文件开头应包含：用途（`@brief`）、核心设计（`@details`）、约束与注意事项（`@note` / `@warning`）。

### 函数注释

对外接口使用 Doxygen 风格：

```c
/**
 * @brief  设置采样率档位
 * @param  idx  时基表索引，超出范围时自动截断
 * @note   切换档位会重新配置 TIM2 分频，DMA 传输过程不中断
 */
void osc_adc_set_timebase(u8 idx);
```

### 命名约定

| 类型 | 规范 | 示例 |
|---|---|---|
| 全局变量 | `g_` 前缀 | `g_wave`, `g_wave_valid`, `g_measure` |
| 静态变量 | `s_` 前缀 | `s_ring`, `s_tb_idx`, `s_hann` |
| 常量 | `s_` 前缀 + `const` | `s_tb[]`, `s_ch_name[]`, `s_hann[]` |
| 宏 | 全大写下划线 | `OSC_RING_SIZE`, `HANN_Q` |
| 函数 | 模块名_动作 | `osc_adc_init`, `osc_trigger_capture` |
| 类型 | `_t` 后缀 | `timebase_t`, `osc_measure_t` |

### 注释原则

| 应注释 | 不应注释 |
|---|---|
| 硬件约束与参数来源 | 语法层面的逐行解释 |
| 算法依据与公式出处 | 显而易见的赋值 |
| 特殊处理的原因（Why） | 代码已表达的"做什么"（What） |
| 调用约束与副作用 | 变更历史（交由版本控制） |

### 分层约束

| 层级 | 允许依赖 |
|---|---|
| `osc_ui.c` | LCD 驱动、各 APP 模块的对外接口、按键驱动 |
| `osc_trigger.c` / `osc_measure.c` / `osc_fft.c` | `osc_adc.h`、`sys.h` |
| `osc_adc.c` | 标准外设库、`sys.h` |
| **禁止** | 驱动层调用界面层；界面层直接操作 ADC/DMA 寄存器 |

### 浮点使用原则

本项目**不使用浮点运算**（除生成常量表的脚本外）。原因：

- Cortex-M3 无硬件浮点单元，浮点运算由软件库模拟，耗时且增大代码体积
- 示波器需要每帧执行测量与 FFT，浮点会成为性能瓶颈

需要小数显示时，采用整数的"千分位拆分"：

```c
sprintf(buf, "%u.%02uV", mv / 1000, (mv % 1000) / 10);
```
